# Changelog and release notes

- `.changelog/unreleased.md` collects the entries of the next release, `CHANGELOG.md` is the running history (newest release first). The rules for the wording are the comment at the top of `unreleased.md`.
- Add the line in the **same commit** as the change, for anything a user or the operator of the Home Assistant app can see. German, in the words of the user interface, from the user's side, with `(#nr)` if an issue drove it.
- A feature that grows over several tickets gets one line as a whole under **Neue Funktionen**, written with the last ticket of the spec (or the merge of the epic): what the user can do now, where it appears, what it does not touch, with the numbers of the tickets, not of the spec. The lines of the single tickets stay and name their own part.
- Sections, always in this order, none removed: `## Vor dem Update` (optional, see below), `## Neue Funktionen`, `## Verbesserungen`, `## Fehlerkorrekturen`, `## Wartung`.
- **Vor dem Update** is one short notice at the top of the release notes, written as plain text starting with `**Vor dem Update:**`. `scripts/release-prepare` turns it into a quote block without a heading and leaves it out when the section is empty. It exists only for two cases: a migration that cannot be undone (no way back to the old version), or numbers of months already recorded that change (balance, settlement, calculation). It says what happens and what changes, not what the user must do (the app backs up the database itself before a migration). The detail stays as a line in **Wartung**.
- **Wartung** is what an operator must know when updating: Go version, base image, environment variables, ports, data paths, migrations, security updates. Dependabot updates and refactorings get one collective line each ("Aktualisierung der Abhängigkeiten", "Interne Aufräumarbeiten am Code ohne sichtbare Änderung"), added by `scripts/release-prepare`, never one line per update or refactoring.
- A ticket that asks for a changelog line: for a feature over several tickets the last ticket writes the one line for the whole feature, the others name only their own part. Read this file before writing the spec, not after the review.
- A change that moves existing numbers (a balance that changes retroactively, a rule that applies to old data) is something an operator must know when updating: it gets its **own line in Wartung** besides the line of the feature, not a "Zu beachten" prefix in another section.
- No line for `docs`, `test`, `style`, `ci`, scripts, hooks, agent rules or a pipeline repair nobody notices. Refactorings only as the one collective line above.
- The history can be revised later at any time: the text of an old GitHub release is changed with `gh release edit <tag> --notes-file <file>` (keep both in step). The `ha-addons` changelog is a copy of `CHANGELOG.md` at the tag and follows at the next release.

## Release notes

`release.yml` creates the GitHub release with `gh release create`. The text is the section of this version from `CHANGELOG.md` (`###` becomes `##`) which ends with the German line `Alle Änderungen im Vergleich: [vA...vB](compare link)` (written into `CHANGELOG.md` by `scripts/release-prepare`). `ha-addon.yml` copies `CHANGELOG.md` at the tag to `ha-addons` unchanged.
